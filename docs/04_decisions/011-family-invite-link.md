# ADR 011: 家族への参加は、宛先指定の招待と本人の承認で行う

## 背景

いま作れるのは家族グループの作成と、作成者本人の所属だけである（Issue #37）。レシピを家族の資産として共有するには、別のユーザーが既存の家族に入れる必要がある（[ADR 005](./005-family-feature.md)）。

現状の `family_members` INSERT ポリシーは `user_id = auth.uid()` だけを見る。家族 ID を知っていれば、誰でも自分を任意の家族に追加できる。参加を作るなら、先にここを閉じて、招待された人だけが入れる仕組みにする必要がある。

ゲストの招待・参加は本登録のみとする（[ADR 007](./007-guest-login.md)）。

初版は「1 回限りの招待リンク（トークン）」だった。2026-10-19 に、ユーザーが「宛先を指定し、相手がログインして承認する」流れを求めたため、方式を改めた（要件: [family-member-join.md](../01_requirements/family-member-join.md)）。

## 決定内容

**オーナーが、相手のメールアドレスを指定した招待を発行する。相手は、そのメールアドレスでログインし、家族管理画面で招待を確かめ、承認して参加する。**

| 項目 | 方針 |
| --- | --- |
| 方式 | 宛先のメールアドレスを指定した招待。1 招待 1 人宛て。複数人は人数分を発行する |
| 案内の渡し方 | アプリはメールを送らない。オーナーが案内の URL を LINE などで渡す |
| 発行・一覧・取り消し | 家族のオーナー（本登録ユーザー）のみ |
| 参加できる人 | 宛先のメールアドレスでログインした、未所属の本登録ユーザー。参加は本人の承認操作に限る |
| 本人の特定 | 宛先のメールアドレスと、ログイン中ユーザーのメールアドレスの一致 |
| 有効期限 | 発行から 1 日 |
| 取り消し | オーナーが、使われていない招待を取り消せる |
| 未ログイン | ログイン後に元の画面へ自動で戻る処理は作らない。本人が家族管理画面を開く。通知一覧は未実装のため使わない |
| 参加の実行 | クライアントから `family_members` へ直接 INSERT しない。検証と所属追加を 1 つの DB 関数でまとめて行う |
| 既存 INSERT | 直接 INSERT は、オーナーが自分を最初のメンバーにする場合だけに絞る |

## なぜこの案か

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 宛先指定の招待 + 本人の承認 | 採用 | 本人の同意なく家族に入れない。ログイン済みのメールアドレスで本人を確かめられ、URL が漏れても他人は承認できない。メール送信基盤を足さずに済む |
| 宛先なしの招待リンク（トークン） | 不採用 | URL を持つ人が入れてしまう。ログイン後に元の案内へ戻す処理が要る。ユーザーが求める「ログイン後に家族管理画面で確かめる」流れに合わない |
| アプリからのメール送信 | 不採用（将来） | 送信基盤（カスタム SMTP）が未導入（確認メール以外のメールを出さない方針）。必要になったら別 ADR で足す |
| 参加コード | 不採用 | 短い文字列は総当たりされやすい。長くすると入力の手間がリンクと変わらない |
| 家族 ID を直接指定 | 不採用 | 現状の穴そのもの。ID を知れば誰でも入れる |
| 誰でも招待を発行できる | 不採用 | 最初の段階ではオーナーに絞り、メンバーの増減を管理しやすくする。必要になったら別 ADR で広げる |

## 結果・利点

- 家族 ID や案内の URL が分かっても、宛先本人でなければ入れない
- 本人が承認するまで、所属は増えない
- ゲストの関門を、DB 関数と RLS の両方に置ける
- 期限（1 日）・取り消し・オーナー限定で、渡し間違いの影響が小さい
- 秘密のトークンを持たないため、トークンの保管や再表示の問題がない

## 考慮点・トレードオフ

- 相手が、招待されたメールアドレスで登録・ログインしていないと承認できない。別のメールアドレスで登録済みの人には、オーナーが宛先を直して再発行する
- 期限が 1 日と短い。承認が遅れたら、オーナーが再発行する
- 宛先のメールアドレスを DB に持つ。本人以外には見せない制御（RLS）が要る
- 招待の宛先が登録済みかどうかを、オーナーに悟らせない設計にする（要件 NFR-04）
- `family_members` INSERT ポリシーの変更は、既存の家族作成フローにも影響する（作成時にオーナー本人を足す処理は通す）
- 1 ユーザー 1 家族は、現状アプリ側の確認だけで DB の一意制約はない。承認でも二重所属を防ぐ必要がある（[family.md](../02_design/domain/family.md) INV-01）。ADR 005 の将来拡張（複数家族）を残すため、一意制約は入れず、関数内で直列化して拒否する案を採る（レビューで確定）
- 本ファイルは、初版のファイル名（`011-family-invite-link.md`）を、リンク切れを避けるため残している
