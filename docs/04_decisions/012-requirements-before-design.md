# ADR 012: 要件定義を設計の前に置き、docs を要件・設計・テストに分ける

## 背景

[ADR 010](./010-issue-centered-dev-flow.md) の流れは、Issue から `/plan`、`/design` へ進むものだった。家族メンバー追加（Issue #37）で設計に入ったとき、「なぜ作るか」「何ができれば足りるか」の整理が文書として無いまま、方式（招待リンク）や DB の設計から書き始めていた。

- 要求と要件が、設計の文書の中に混ざる。レビューで「そもそも何を満たすべきか」を確かめにくい
- 設計に出てくる判断が、要件から来たのか、設計者の都合なのかが分からない
- `docs/` は層（`01_architecture`〜`06_ui`）で並んでおり、「何を作るか → どう作るか → どう確かめるか」の段階が見えない
- テスト設計は、操作メモ（04）や画面（06）の中の 1 節に埋まっており、戦略（07）と別の場所にあって探しにくい

## 決定内容

**設計の前に要件定義を置く。** 流れは次のとおり。

```text
Issue → /plan → /requirements（要件定義）→ 要件定義のレビュー
  → /design（設計・テスト設計）→ 設計のレビュー → レビュー後の承認 → 実装
```

- 新しい Skill `define-requirements` と Command `/requirements` を置く。`write-design` は、要件定義が無い・未確定のときは始めない
- Issue の実装開始条件に「要件定義の確定」を足す。付けるのは人間
- 設計・テスト設計は、要件の ID（`FR-` / `NFR-`）を参照する。要件に無いことを設計で足さない
- `docs/` を、要件・設計・テストの段階で分ける。ディレクトリ名は英語にする

| 新 | 役割 | 旧 |
| --- | --- | --- |
| `01_requirements` | 何を作るか、なぜ作るか。機能ごとに 1 ファイル | （新設） |
| `02_design/architecture` | 構造とデータの流れ | `01_architecture` |
| `02_design/domain` | 仕様（ルール・状態・権限） | `02_domain` |
| `02_design/database` | テーブル・RLS・Storage | `03_database` |
| `02_design/application` | 操作（usecase）の設計 | `04_application` |
| `02_design/api` | API | `05_api` |
| `02_design/ui` | 画面・遷移 | `06_ui` |
| `03_test` | 戦略・範囲・E2E・インシデント | `07_testing` |
| `03_test/design` | 操作ごとのテスト設計 | 旧 `04_application` と `06_ui` の「テスト設計」節 |
| `04_decisions` | ADR | `09_decisions` |
| `05_development` | 開発の手順・規約 | `08_development` |
| `90_workspace` | 作業用（ハーネス・学習・レビュー） | 変更なし |

## なぜこの案か

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 要件を Issue だけに書く | 不採用 | Issue は短い目的・理由・範囲にとどめる（ADR 010）。要件は ID をつけて、設計・テスト設計から参照できる必要がある |
| 要件を `domain` の仕様に含める | 不採用 | 仕様は「ルール・状態・権限」。要件は「なぜ・何が要るか」。混ぜると仕様が肥大し、要件に無い仕様が入っても気づけない |
| 層ごとの並びのまま、要件だけ足す | 不採用 | 「何を作るか → どう作るか → どう確かめるか」の段階が見えない |
| テスト設計を操作メモに残す | 不採用 | 検証の観点がレビューで見落とされやすい。戦略と操作別が別の場所になる |
| 機能ごとに束ねる（`design/family/...`） | 不採用 | 層をまたぐ共通部分（ER、遷移図）の置き場が曖昧になる。移行の差分も大きい |

## 結果・利点

- 設計が要件のどれに応えているかを、ID でたどれる
- 要件のレビューを、設計のレビューから切り離せる
- テスト設計が一か所にまとまり、設計と同じ構成で探せる

## 考慮点・トレードオフ

- 工程が増える。軽微な変更は `/plan` が「要件定義は不要」と理由を書いて落とす
- 既存機能の要件定義は未作成。改定するときに足す（一括では作らない）
- パスが変わるため、過去の Issue や PR にある旧パスのリンクは切れうる
- 既存の操作メモにはテスト設計の無いものがある。改定するときに `03_test/design` へ足す
