# ADR 013: プロセスごとに Issue・ブランチ・PR を分け、Issue は各プロセスの開始時に作る

## 背景

[ADR 010](./010-issue-centered-dev-flow.md) は、1 つの Issue に、目的・範囲・完了条件と、実装開始条件のチェックリストを置いた。[ADR 012](./012-requirements-before-design.md) で要件定義が加わり、実装開始条件の項目が 7 つに増えた。

家族メンバー追加（Issue #37）で、次の困りごとが出た。

- 要件定義・設計・実装の進み具合が、1 つの Issue のチェックリストにまとまり、どのプロセスが済んで何が残っているか分かりにくい
- 1 本のブランチに、要件定義も設計も積まれ、PR が大きくなる。プロセスごとのレビューの記録が埋もれる
- 実装を発行側と参加側に分けたいが、1 つの Issue のままでは「1 操作 = 1 PR」に合わせにくい

## 決定内容

**開発対象（親 Issue）の下に、プロセスごとの子 Issue（sub-issue）を切る。1 プロセス = 1 Issue = 1 ブランチ = 1 PR とし、前のプロセスの PR がマージされてから、次のプロセスを始める。**

```text
develop → 親 Issue → 要件定義 → 設計 → テスト設計 → 実装（操作ごと）
                     各プロセス: Issue → ブランチ → 作業 → PR → マージ → Issue を閉じる
```

- 子 Issue は、そのプロセスを始めるときに、そのプロセスの Skill が作る。前のプロセスの Issue が閉じていること（PR がマージ済み）を確かめてから作る
- ブランチは、Issue を作ったあとに、Skill が `origin/develop` からローカルで切る。push しない
- 親 Issue は、`/plan` が下書きを出し、ユーザーが OK したあとに作る
- テスト設計を、設計から切り離して独立したプロセスにする（Skill `write-test-design`、Command `/test-design`）
- 要件定義 Issue と設計 Issue とテスト設計 Issue は、そのプロセスの完了条件（書いた、レビュー）を持つ。実装 Issue は、従来どおりの実装開始条件（Ready）を持つ
- Issue のチェックと、子 Issue を閉じることは、人間だけが行う。AI は作るだけ
- 本文の骨格、ブランチ名、始め方は [issue-workflow.md](../05_development/issue-workflow.md)

## なぜこの案か

| 案 | 採否 | 理由 |
| --- | --- | --- |
| プロセスごとに Issue・ブランチ・PR を分け、次の Issue は前の PR のマージ後に作る | 採用 | PR が小さくなり、プロセスごとにレビューの記録が残る。前のプロセスで決まったことを踏まえて、次の Issue を書ける |
| 次の Issue を、前のプロセスの Skill の終わりに先回りして作る | 不採用 | 前の PR のレビューで内容が変わると、先に作った Issue が古くなる。1 本のブランチに積まれやすい |
| 1 つの Issue のチェックリストのまま | 不採用 | プロセスが増えるほど、1 つの Issue が大きくなる。実装を操作ごとに分けにくい |
| 親を置かずに独立した Issue | 不採用 | プロセス間のつながりが本文のリンクだけになり、全体の進み具合を一覧できない |
| 最初に全プロセスの Issue を作る | 不採用 | 設計の中身が分からないうちは、実装 Issue を何件に分けるかが決まらない |
| テスト設計を設計に含める | 不採用 | 設計のレビューが重くなる。何を作るかの設計と、どう確かめるかの設計を、別の PR で見たい |

## 結果・利点

- どのプロセスが済み、何が残っているかを、子 Issue の一覧と PR で見られる
- PR がプロセス単位になり、レビューしやすい
- 実装を、設計が決まった操作の単位で分けられる（1 操作 = 1 PR）

## 考慮点・トレードオフ

- Issue・ブランチ・PR の数が増える。軽微な変更（要件定義も設計も不要）は、必要なプロセスだけを回す
- 次のプロセスは、前の PR のマージを待つ。待っている間は、別の開発対象を進められる
- 実装開始条件の項目は、実装 Issue にも残る（要件定義の確定など）。前のプロセスの Issue と二重になるが、実装を始める人が 1 か所で確かめられる形を優先する
- sub-issue の作成に GitHub の機能と `gh` の `--parent` を使う。使えない環境では、本文に親の番号を書く
- ひな形は GitHub の Issue フォームと、AI が書く本文の 2 か所にある。項目は [issue-workflow.md](../05_development/issue-workflow.md) に合わせる
