# レシピ更新

## スコープ

### 含める

- 既存レシピの本文・人数・時間・下書き／公開・材料・手順・カテゴリ・サムネイルの更新
- 作者本人だけが更新できる
- 詳細画面から `/recipe/[id]/edit` へ進む導線
- Server Action + 編集画面

### 含めない（別ブランチ / 別 PR）

- レシピ削除
- 家族メンバーによる編集
- 手順画像の Storage 保存（現状は作成・更新ともに `image_url` を保存していない）
- HEIF 対応

## 各層の流れ

```
edit/page.tsx（作者以外は 404）
  → RecipeForm（作成と共用。recipe を渡すと編集モード）
    → updateRecipeAction（deps 組み立て・エラーの表示用変換・revalidate）
      → updateRecipeUsecase（入力チェック・作者チェック・旧サムネイル削除）
        → updateRecipeWithRelations（RPC で 1 トランザクション更新）
```

## 決めたこと

### 更新は 1 トランザクションにする

材料・手順・カテゴリは「全削除 → 再挿入」で置き換える。作成時と違い、更新では途中で失敗すると
既存データが消えたまま残るため、本体の更新と関連データの入れ替えを Postgres 関数
`update_recipe_with_relations` にまとめている（`security invoker` なので RLS はそのまま効く）。

### 書き込みは作者のみに揃える

RLS は当初「家族メンバーも公開レシピを更新・削除できる」「子テーブルの delete は閲覧できる人なら誰でも」
だったが、アプリは作者本人しか更新しないため DB 側も作者のみに寄せた
（`20260913000003_recipe_write_policies_author_only.sql`）。家族メンバーの編集を解禁するときは、
アプリの認可とポリシーを同時に戻すこと。

### 入力チェックは usecase に置く

料理名・人数・調理時間の検証は `validateRecipeContent` に集約し、作成・更新の両方から呼ぶ。
app 層で 0 を 1 に補正するような暗黙の変換はしない。

### サムネイルの後始末

差し替え・削除で参照されなくなった画像は Storage から消す。消せなくても更新自体は成功しているため、
失敗はログに残すだけで握りつぶす。

### 下書きの扱い

編集画面のボタン文言は状態で変える（公開済み: 「変更を保存」「下書きに戻す」/ 下書き: 「公開して保存」「下書きのまま保存」）。
