## 1. 背景と課題

- いま作れるのは、家族グループの作成と、作成者本人の所属だけである。メンバーは作成者 1 人から増やせない
- レシピの共有は「同じ家族のメンバーに公開レシピが読める」ことで成り立つ。メンバーが 1 人のままでは、共有は起きない
- 現状、家族に入るための条件は「本人が家族 ID を指定する」ことだけで、家族側が「入ってよい人」を選べていない。家族の外の人が入れてしまう余地がある

## 2. なぜ作るか

- **目的:** 家族の一員を、既存の家族グループに迎えられるようにする
- **価値:** 家族全員が同じレシピを読める。「家族の味を、ここに残そう」というコンセプトが、1 人の記録帳から家族の共有財産になる
- **成功の姿:** 家族のオーナーが、家族に入ってほしい人を招待する。招待された人は、自分でログインして招待を確かめ、承認して家族に入る。関係のない人は入れない

## 3. 利用者と要求

| ID | 利用者 | 要求（〜したい。なぜなら〜） |
| --- | --- | --- |
| R-01 | 家族のオーナー | 家族に入ってほしい人を、自分の家族に招待したい。なぜなら、家族のレシピを一緒に見られるようにしたいから |
| R-02 | 家族のオーナー | 発行した招待の状況を確かめ、誤って送った招待は取り消したい。なぜなら、違う人に家族へ入られたくないから |
| R-03 | 招待される人（本登録ユーザー） | 自分宛ての招待を確かめ、納得したうえで家族に入りたい。なぜなら、勝手に家族へ入れられたくないし、家族のレシピをすぐ見たいから |
| R-04 | 家族のオーナー・メンバー | 関係のない人に勝手に家族へ入られたくない。なぜなら、家族のレシピは外に出したくないから |
| R-05 | ゲスト（体験中の利用者） | 体験の範囲では他人に影響が出ないでほしい。なぜなら、本登録していない人が他人の家族に入ったり、人を入れたりするのは安全でないから |

## 4. 利用の流れ（利用者の視点）

細部は設計で決める。ここでは、利用者がたどる大筋だけを示す。

1. オーナーが、家族管理画面で、招待したい人のメールアドレスを入れて招待を発行する
2. オーナーが、案内の URL を LINE などで相手に渡す（アプリはメールを送らない）
3. 相手が URL を開く。未ログインならログインする（まだアカウントが無ければ、そのメールアドレスで登録する）
4. 相手が、家族管理画面で自分宛ての招待を確かめる。通知一覧は未実装のため、確かめる場所は家族管理画面とする
5. 相手が、承認画面を開いて承認ボタンを押す。家族のメンバーになる
6. オーナーは、一覧で状況を確かめる。まだ使われていない招待は、取り消しボタンで取り消せる

## 5. 要件

### 5.1 機能要件

| ID | 要件 | 応える要求 | 優先度 |
| --- | --- | --- | --- |
| FR-01 | オーナーは、招待したい人のメールアドレスを指定して、家族への招待を発行できる。1 つの招待は 1 人宛てとする | R-01 | 必須 |
| FR-02 | オーナーは、複数の人を招待できる（人数分の招待を発行する） | R-01 | 必須 |
| FR-03 | オーナーは、案内の URL を LINE などで相手に渡せる | R-01 | 必須 |
| FR-04 | オーナーは、期限内で未使用の招待の一覧（宛先、期限）を家族管理画面で確かめられる。取り消し済み・期限切れ・承認済みの招待は一覧に出ない | R-02 | 必須 |
| FR-05 | オーナーは、まだ使われていない招待を、取り消しボタンで取り消せる。取り消した招待は承認できない | R-02 | 必須 |
| FR-06 | 招待は、発行から 1 日で期限が切れる | R-04 | 必須 |
| FR-07 | 招待された人（宛先のメールアドレスでログインした本登録ユーザー）は、家族管理画面で、自分宛ての招待（家族名）を確かめられる | R-03 | 必須 |
| FR-08 | 招待された人は、承認画面で承認ボタンを押すことで、自分の操作で、その家族のメンバーになれる | R-03 | 必須 |
| FR-09 | 参加した本人が、その家族のメンバーとして確認できる | R-03 | 必須 |
| FR-10 | 承認できない招待（期限切れ、取り消し済み、承認済み、宛先違い）は、承認できず、そのことと次の行動（オーナーに再発行を頼む）が分かる | R-03 | 必須 |
| FR-11 | すでに家族に所属している人は、別の家族に参加できない（現行の 1 人 1 家族） | R-04 | 必須 |
| FR-12 | 招待の発行・一覧・取り消しができるのは、その家族のオーナーだけである | R-04 | 必須 |
| FR-13 | 未ログインでは承認できない。ログインが必要と分かる。ログイン後に承認画面へ自動で戻る処理は要らず、本人が家族管理画面から進めばよい | R-04 | 必須 |
| FR-14 | ゲストは、招待の発行も承認もできない。本登録が必要と分かる | R-05 | 必須 |
| FR-15 | 同じ宛先に、期限内で未使用の招待があるときは、重ねて発行できない。取り消すか期限切れを待てば、あらためて発行できる | R-02 | 必須 |
| FR-16 | 家族の人数（オーナーを含む）が上限の 6 人に達しているときは、承認できず、そのことが分かる | R-04 | 必須 |

### 5.2 非機能要件・制約

| ID | 要件 | 観点 | 優先度 |
| --- | --- | --- | --- |
| NFR-01 | 家族を特定する情報（家族 ID）や招待の URL が分かっても、それだけでは参加できない。参加できるのは、宛先のメールアドレスで認証された本人が、承認の操作をしたときだけである | セキュリティ | 必須 |
| NFR-02 | 他人を本人の同意なく家族に追加しない。参加は、本人が承認ボタンを押したときに限る | プライバシー | 必須 |
| NFR-03 | 承認する前の人に、家族名以外の家族の情報（メンバー、レシピ）を見せない | プライバシー | 必須 |
| NFR-04 | 招待の発行で、宛先のメールアドレスがすでに登録済みかどうかが、オーナーに分からない | プライバシー | 必須 |
| NFR-05 | 他人宛ての招待を、見ることも承認することもできない | セキュリティ | 必須 |
| NFR-06 | 既存の家族作成の流れを壊さない | 互換性 | 必須 |
| NFR-07 | 人数の上限は、将来、課金状況に応じて変えられる形にする。今回は全家族一律 6 人とし、上限を変えるために、承認の仕組みそのものを作り直さずに済むこと | 拡張性 | 必須 |

## 6. スコープ

| 含める | 含めない |
| --- | --- |
| 招待の発行（宛先のメールアドレス指定、オーナー） | アプリからのメール送信（案内の URL はオーナーが渡す） |
| 発行した招待の一覧と取り消し（オーナー） | 通知一覧（未実装。家族管理画面で代える） |
| 自分宛ての招待の確認と承認による参加（本登録ユーザー） | ログイン後に元の画面へ自動で戻る処理 |
| 参加後にメンバーとして確認できること | 1 つのリンクを複数人が使う方式 |
| 使えない招待のときの案内 | 家族の新規作成（既存） |
| ゲスト・所属済みの拒否 | 脱退、グループ名の変更、グループの解散 |
| | オーナーによる他メンバーの強制追加・削除 |
| | 招待された人の辞退ボタン（辞退したいときは期限切れを待つ） |
| | 同じ宛先への、期限内の招待の重ね発行 |
| | 課金機能、プランごとの人数の上限の切り替え（今回は一律 6 人。変えやすい形にするところまで） |
| | 複数家族への同時所属、家族の切り替え |
| | ゲストによる招待・参加（本登録後に使える） |
| | 家族メンバーによるレシピ編集権限の変更 |

## 8. 受け入れ条件

利用者から見て、次ができたら足りる（Issue #37 の完了条件を含む）。

発行側:

- [ ] オーナーが、メールアドレスを指定して招待を発行でき、複数人分を発行できる
- [ ] オーナーが、期限内で未使用の招待の一覧（宛先、期限）を確かめられる。取り消し済み・期限切れ・承認済みは出ない
- [ ] オーナーが、まだ使われていない招待を取り消せる。取り消した招待は承認できない
- [ ] オーナーでない人は、招待の発行・一覧・取り消しができない
- [ ] 招待は発行から 1 日で期限が切れる

参加側:

- [ ] 宛先のメールアドレスでログインした人が、家族管理画面で自分宛ての招待を確かめられる
- [ ] 承認ボタンを押すと、その人が家族のメンバーになる。参加後、メンバーとして本人が確認できる
- [ ] 期限切れ・取り消し済み・承認済みの招待は承認できず、案内が出る
- [ ] 他人宛ての招待は、見ることも承認することもできない
- [ ] すでに家族に所属している人は、別の家族に参加できない
- [ ] 家族の人数（オーナーを含む）が 6 人に達しているときは、承認できず、案内が出る
- [ ] 未ログインでは承認できない
- [ ] ゲストは、発行も承認もできない
- [ ] 家族 ID や招待の URL だけでは、家族に入れない
- [ ] 既存の家族作成が、これまでどおりできる

## 10. 設計への申し送り

設計で決める。ここでは決めない。

- 現行の所属追加の条件（本人が自分を追加できる）が、NFR-01 を満たしていない。見直しが要る
- ゲストを判定する仕組みが DB 側にまだ無い。FR-14 は、画面だけでなくデータ側でも守る必要がある
- 人数の上限（6 人）の持ち方を決める。課金状況で変えられる余地（NFR-07）を、今回の範囲で作り込みすぎずに残す方法にする
- 人数の上限（FR-16）の判定と、同時に承認されたときの超過防止を、二重所属の防止と同じ仕組みで扱えるか決める
- 同じ宛先への重ね発行（FR-15）を、取り消し済み・期限切れ・承認済みの招待と区別して、どう防ぐかを決める
- 承認の時点で、ログイン中ユーザーのメールアドレスが確認済みかを、DB 関数の中でも確かめるか決める（確認の仕組みが決まってから）
- 招待された人の特定は、宛先のメールアドレスとログイン中のユーザーの一致で行う。メールアドレスの比較（大文字小文字など）と、他人に見せない保ち方（NFR-05）を決める
- 招待の状態（待ち、承認済み、取り消し済み、期限切れ）の持ち方と、期限の判定を決める
- 承認による所属追加と、招待の使用済み化は、1 つの操作として扱う必要がある（同時操作でも 1 回だけ）
- 二重所属を、同時操作でも防ぐ必要がある（FR-11）
- 承認する前の人に見せる情報の範囲（NFR-03）と、一覧に出す宛先情報を、DB のアクセス制御でどう守るか
- 案内の URL に秘密のトークンが要るか。宛先とログインで本人を確かめるため、要らない見込みだが、設計で決める
- 失敗の理由を、画面でどこまで区別して見せるか（FR-10 と、他人の招待の存在を推測させない NFR-05 の両立）
