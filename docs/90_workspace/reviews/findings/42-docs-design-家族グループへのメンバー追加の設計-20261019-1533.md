## 良い点

- ADR 011 は宛先指定＋承認に更新済みで、方式の正は読める
- ゲスト関門を UI だけにしない方針（usecase と RLS の両方）は書かれている
- 参加を `security definer` の 1 トランザクションにまとめる方針は、途中失敗の残留を避けられる

## 改善点

### 1. 招待リンク（トークン）方式が、確定済み要件・ADR と食い違う（重要度: 高）

- 状態: 対応済み
- 観点: 要件整合、セキュリティ（NFR-01）
- 対象: `docs/02_design/domain/family.md`、`docs/02_design/application/family/*.md`、`docs/02_design/database/tables/family_invites.md`、`docs/02_design/ui/screens/family.md`、`docs/02_design/ui/screens/family-join.md`
- 現状: 確定済み要件と [ADR 011](../../../04_decisions/011-family-invite-link.md) は、宛先メール指定の招待と、本人が家族管理画面で確かめて承認する流れである。秘密のトークンは持たない。設計書は、トークン付き URL（`/family/join/{token}`）、`token_hash`、発行直後だけリンクを見せる方式のままである
- 改善案: 要件・ADR 011 に合わせて、招待リンク（トークン）の仕様・設計を宛先指定＋承認に作り直す。案内の URL に秘密が要るかは、ADR の「要らない」を正として設計に落とす
- 理由: 方式が違うと、画面・テーブル・権限・失敗の意味がすべてずれる。URL を持つ人が入れる設計は NFR-01（家族 ID や URL だけでは参加できない）を満たさない
- 正本の根拠: `docs/01_requirements/family-member-join.md`（FR-01、FR-07、FR-08、NFR-01、設計への申し送り）、`docs/04_decisions/011-family-invite-link.md`
- 対応: 2026-10-19。トークンを廃止。宛先メール、案内 URL は `/family`、承認画面は `/family/join`（新規）に作り直した

### 2. 要件の「設計への申し送り」が仕様・設計に落ちていない（重要度: 高）

- 状態: 対応済み
- 観点: 要件整合、セキュリティ（認可・PII・同時実行）
- 対象: `docs/01_requirements/family-member-join.md` §10、`docs/02_design/domain/family.md`、`docs/02_design/database/`、`docs/02_design/application/family/`
- 現状: 申し送りのうち、次が決まっていない、またはトークン案のままである

| 申し送り | 設計の状態 |
| --- | --- |
| 所属追加の条件（NFR-01）。現行 INSERT は家族 ID だけで入れる | `family_members.md` に変更予定とあるだけ |
| ゲスト関門を DB 側でも守る（FR-14） | `is_permanent_user()` の言及はある。判定の正は未確定 |
| 人数上限 6 人の持ち方（FR-16、NFR-07） | 未記載 |
| 同時承認での人数超過・二重所属の防止 | リンク同時使用の直列化だけ。上限超過は未記載 |
| 同じ宛先への重ね発行防止（FR-15） | 未記載 |
| 承認時にメール確認済みかを DB 関数でも見るか | 未記載 |
| メールアドレスの比較（大文字小文字）と、宛先を他人に見せない保ち方（NFR-04、NFR-05） | 宛先カラム自体が無い |
| 承認前に見せる情報と、一覧の宛先を RLS でどう守るか（NFR-03） | トークン照会関数の話に留まっている |
| 失敗理由の区別（FR-10）と、他人の招待を推測させないこと（NFR-05）の両立 | 「使えない」にまとめる案のみ。宛先違いの扱いは未決 |

- 改善案: 申し送りを 1 項目ずつ、ドメインの不変条件・操作・失敗の意味と、DB / application の決めたことに落とす。足したくなった要求は要件定義へ戻す
- 理由: Issue #42 の目的は、この申し送りを扱うことである。未決のまま実装に入ると、認可と PII の穴がコードで決まる
- 正本の根拠: `docs/01_requirements/family-member-join.md` §9〜§10、`docs/05_development/issue-workflow.md`
- 対応: 2026-10-19。INV-01/08/09/10、`family_member_limit()`、`is_permanent_user()`、メール正規化、失敗の区別、INSERT ポリシーの絞り込み、Q-03 を設計に落とした

### 3. 発行・一覧・取り消し・承認が、操作として分かれていなかった（重要度: 中）

- 状態: 対応済み
- 観点: 仕様の操作分割、画面の主目的
- 対象: `docs/02_design/application/family/`、`docs/02_design/ui/screens/family.md`、`docs/02_design/domain/family.md`
- 現状（レビュー時）: application は発行と参加の 2 操作だけだった。一覧・取り消しはドメインの未決で後回しにされていた
- 改善案: application / UI を発行・一覧・取り消し・承認に分ける。取り消しは Secondary
- 理由: 1 操作 1 PR の実装に入る前に、操作の境界が設計に無いと Issue の切り方が決まらない
- 正本の根拠: `docs/01_requirements/family-member-join.md`（FR-01、FR-04、FR-05、FR-08）、`.cursor/rules/file-naming.mdc`、`.cursor/rules/ui-design.mdc`
- 対応: 2026-10-19 に反映した。`list-family-invites.md` / `cancel-family-invite.md` を追加。ドメインに OP-04、Q-02、INV-07、招待の状態。家族管理画面に期限内未使用の一覧と取り消し。`family_invites.revoked_at`

### 4. テスト設計が、設計ブランチに混在していた（重要度: 中）

- 状態: 対応済み
- 観点: プロセス分離
- 対象: `docs/03_test/design/family/`、`docs/03_test/design/README.md`、`docs/.vitepress/config.mts`
- 現状（レビュー時）: テスト設計 2 ファイルと VitePress の Test design リンクが入っていた。中身はトークン案向け
- 改善案: この PR から外し、`/test-design` で設計 Issue が閉じたあとに書く
- 理由: 1 プロセス = 1 Issue = 1 ブランチ = 1 PR。混ぜると方式変更時の作り直し漏れが起きる
- 正本の根拠: `.cursor/skills/write-design/SKILL.md`、`docs/05_development/issue-workflow.md`、`docs/04_decisions/013-issue-per-process.md`
- 対応: 2026-10-19 に反映した。テスト設計ファイルを削除し、一覧・VitePress・要件定義からのリンクを外した

### 5. ドメインの未決（7 日期限・取り消し後回し）が要件と矛盾していた（重要度: 中）

- 状態: 対応済み
- 観点: 仕様の未決、セキュリティ（招待の寿命）
- 対象: `docs/02_design/domain/family.md`、`docs/02_design/application/family/create-family-invite.md`、`docs/02_design/database/tables/family_invites.md`、`docs/02_design/ui/screens/family.md`
- 現状（レビュー時）: 有効期限 7 日（草案）。一覧・取り消しは未決で、取り消し UI は禁止
- 改善案: 期限を 1 日に固定。一覧・取り消しをスコープと操作に入れる。招待に未使用 / 使用済み / 取り消し済み / 期限切れを書く
- 理由: 仮置きの 7 日と「取り消し禁止」が本番仕様になる。取り消せない招待は、渡し間違いの影響が残る
- 正本の根拠: `docs/01_requirements/family-member-join.md`（FR-04、FR-05、FR-06）、`docs/04_decisions/011-family-invite-link.md`、`docs/02_design/domain/writing-guide.md`
- 対応: 2026-10-19 に反映した。INV-05 を 1 日・未取り消しに更新。OP-04 / Q-02 と `revoked_at` を追加。§13 から期限と取り消しを削除した

### 6. 二重所属の防止が、一意制約か関数内直列化か未確定（重要度: 中）

- 状態: 対応済み
- 観点: 同時実行、セキュリティ（認可の穴の閉じ方）、拡張性
- 対象: `docs/04_decisions/011-family-invite-link.md`、`docs/02_design/domain/family.md`（INV-01）、`docs/02_design/database/tables/family_members.md`
- 現状: ADR 011 は「一意制約は入れず、関数内で直列化して拒否する」案で、末尾が「レビューで確定」。INV-01 は作成時にだけ保証すると書いてある
- 改善案: 次のどちらかを決める。(1) 一意制約なし + 参加用 DB 関数内で直列化して拒否（ADR 011 の案）(2) `family_members.user_id` に一意制約を足す。決めたら ADR の「レビューで確定」を消し、INV-01 を作成時と参加時にする。人数上限（FR-16）の同時超過も同じ仕組みで扱えるかをセットで書く
- 理由: 同時に 2 つの招待を承認すると、1 人 2 家族や 7 人目が通りうる。一意制約は将来の複数家族（ADR 005）を閉じる。関数内直列化は、関数を通らない INSERT が残っていると効かない
- 正本の根拠: `docs/04_decisions/011-family-invite-link.md`、`docs/04_decisions/005-family-feature.md`、`docs/01_requirements/family-member-join.md`（FR-11、FR-16）
- 対応: 2026-10-19。(1) を採用。INV-01 を作成時・承認時に。人数上限も同じ関数内の直列化。直接 INSERT はオーナー本人の追加だけに絞る
