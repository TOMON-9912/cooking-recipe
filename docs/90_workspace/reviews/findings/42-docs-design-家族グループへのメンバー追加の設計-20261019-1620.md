## 良い点

- ADR 011・domain・テーブル・application・画面が、宛先メール＋本人承認で一致している。秘密のトークンは残っていない
- 案内 URL は `/family`。承認画面 `/family/join` は実装未作成と明記してある
- 自分宛ての失効理由（FR-10）と、他人宛て／存在しない招待（NFR-05）を分けている
- `family_members` の直接 INSERT をオーナー本人の追加に絞り、承認は DB 関数に閉じている
- 人数上限は `family_member_limit()` 1 箇所。ゲストは `is_permanent_user()`。発行では宛先の登録有無を見ない

## 改善点

### 1. 重ね発行の拒否が usecase ロックに依存し、RLS INSERT では抜けうる（重要度: 高）

- 状態: 対応済み
- 現状: 重ね発行（FR-15）は usecase が家族行を `FOR UPDATE` してから照会・INSERT する。RLS の INSERT はオーナーかつ本登録なら通る。部分 UNIQUE は `now()` のため付けない、と書いてある
- 改善案: 発行も承認と同様、検証付きの DB 関数に閉じるか、期限内未使用を表す方法（状態列など）で UNIQUE を付ける。クライアントの直 INSERT だけでは二重に作れないようにする
- 理由: 正規の Action を通さないクライアントでも、同じ宛先の未使用招待を 2 件入れられる。INV-09 が UI だけの保証になる
- 正本の根拠: `docs/01_requirements/family-member-join.md` FR-15、INV-09、`.cursor/skills/review-design/checklist.md` 2.2 / 2.7
- 対応: 2026-10-19。発行を `create_family_invite` に閉じ、INSERT ポリシーを無しにした。部分 UNIQUE は付けない（`now()`）

### 2. 招待の UPDATE ポリシーが、取り消し以外の列まで変えうる（重要度: 中）

- 状態: 対応済み
- 現状: `owner can revoke unused invites` は、未使用かつ未取り消しの行をオーナーが UPDATE できる、とある。`revoked_at` 以外（`used_by` / `used_at` / `invited_email`）を変えられない列制約は書いていない
- 改善案: WITH CHECK で立ててよい列を `revoked_at` に限るか、取り消し用の DB 関数だけが UPDATE できるようにする。使用済み化は承認関数のみ、のままにする
- 理由: 直 UPDATE で使用済みに見せかける、または宛先を書き換えると、承認の契約と一覧が壊れる
- 正本の根拠: `docs/02_design/database/tables/family_invites.md`、checklist 2.2 / 2.6
- 対応: 2026-10-19。取り消しを `cancel_family_invite`（`revoked_at` のみ）に閉じ、UPDATE ポリシーを無しにした

### 3. 新規 security definer の実行権限と search_path が未記載（重要度: 中）

- 状態: 対応済み
- 現状: 承認と自分宛て照会は `security definer` と書いてある。関数名、`GRANT EXECUTE` の相手、`search_path` は無い。既存ヘルパーは ADR 006 で `set search_path = public, pg_temp` としている
- 改善案: 関数名を決め、`authenticated` のみ実行可（`anon` / `public` には付けない）、`search_path` は ADR 006 に合わせると書く
- 理由: definer は RLS を跨ぐ。実行権限と search_path が無いと、実装時にデフォルトの緩い GRANT や search_path ハイジャックが残る
- 正本の根拠: `docs/04_decisions/006-rls-helper-functions.md`、checklist 2.6
- 対応: 2026-10-19。`family_invites.md` に関数名、`GRANT EXECUTE` は `authenticated` のみ、`search_path = public, pg_temp` を書いた

### 4. 既に家族に入っている人の、自分宛て招待の確認（FR-07）が画面に無い（重要度: 中）

- 状態: 対応済み
- 現状: FR-07 は、宛先メールでログインした本登録ユーザーが家族管理で自分宛ての招待（家族名）を確かめられる、とある。所属条件は無い。画面は「未所属かつ自分宛て招待あり」のときだけ確認と承認導線を出している。所属済みは概要または発行が主目的
- 改善案: 所属済みでも Q-03 を出し、承認できない理由（既に家族がある）が分かるようにする。Primary は変えない（オーナーなら発行、メンバーなら概要）
- 理由: 既所属でも招待は届きうる。画面に出さないと、確かめられず、承認できないことにも気づけない
- 正本の根拠: `docs/01_requirements/family-member-join.md` FR-07、FR-11
- 対応: 2026-10-19。所属済みでも家族名を出し、承認できない理由を書く。承認画面へは出さない。Q-03 は所属を問わない

### 5. メール一致の正が JWT か auth.users.email か書いていない（重要度: 低）

- 状態: 対応済み
- 現状: 承認関数は `lower(invited_email) = lower(ログイン中の email)` とある。保存は小文字。JWT と `auth.users.email` のどちらを正にするかが無い
- 改善案: 正を `auth.users.email`（確認済みの登録メール）に固定し、JWT のメールだけに頼らない、と書く
- 理由: 本人確認の土台は登録時のメール確認である。比較対象が揺れると、宛先違いの判定が実装者ごとに変わる
- 正本の根拠: `docs/01_requirements/family-member-join.md` 前提（メールアドレスの確認）、NFR-01、checklist 2.7
- 対応: 2026-10-19。比較の正を `auth.users.email`（`id = auth.uid()`）に固定。JWT の email クレームは正にしない
