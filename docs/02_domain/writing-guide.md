# ドメイン設計書の書き方

新しい関心事（レシピ、家族、ユーザーなど）を実装する前に、リポジトリの `docs/02_domain/_template.md` をコピーして `docs/02_domain/{関心事}.md` を書く。テンプレート本体は VitePress のビルド対象外である。

この文書は **何が正しいか** を固定する。テーブル定義・画面部品・usecase の関数名は書かない。

## コピー後にやること

1. 見出しをドメイン名にする
2. 表の「ステータス」を草案にする
3. セクション 1〜4 を先に埋める（存在理由・スコープ・用語・境界）。ここが空のまま 5 以降に進まない
4. 不変条件と操作に ID を振る（`INV-01`, `OP-01`）。実装・テストから同じ ID を参照できるようにする
5. 未決は「13. 未決」に残し、仮置きのまま本番仕様にしない
6. 受け入れの目安がチェックできない文なら、まだドメインが書けていない

## 他ドキュメントとの分担

| 知りたいこと | 書く場所 |
| --- | --- |
| 何が正しく、誰が何をしてよいか | **このディレクトリの設計書** |
| カラム・RLS・インデックス | [03_database](../03_database/tables/README.md) |
| 画面の導線・コピー | [06_ui](../06_ui/screen-flow.md) |
| なぜその技術にしたか | [09_decisions](../09_decisions/001-architecture.md) |
| どのファイルが実装か | [04_application](../04_application/use-cases.md) |

ドメイン設計書と DB 定義が食い違うときは、**業務ルールはドメイン側を正**とし、テーブル定義を追従させる。

## テンプレートの章が必要な理由

| 章 | ないと起きること |
| --- | --- |
| 存在理由・スコープ | 関係ない機能が同じ「ドメイン」に混ざる |
| 用語 | ユーザー / プロフィール / アカウントがコードと画面でずれる |
| 集約と識別 | 更新漏れ・単体で存在できない行を API が量産する |
| 不変条件 | UI バリデーションだけになり、直アクセスで壊れる |
| 状態 | 下書きと公開の見え方が実装者ごとに違う |
| 操作・照会 | 「画面があるから正しい」になり、権限が画面依存になる |
| 権限と可視性 | アプリと RLS が別ルールになる |
| 整合性 | 親だけ更新され子が古い、または一部だけ残る |
| 失敗 | エラーメッセージとリトライ可否が場当たりになる |
| 永続化の意図 | 画像本体や秘密をテーブルに置いてしまう |
| 未決 | 仮置きが本番仕様として固定される |
| 受け入れ | レビューが「動いた」だけで終わる |
