# 設計を書くときの点検

`write-design` が、各段階の終わりに読む。プロダクト固有の正解は `docs/01_requirements`〜`docs/04_decisions` を正とし、ここにコピーしない。レビュー用の厚い観点は `.cursor/skills/review-design/checklist.md`。

## 全段階

- 確定済み要件の FR / NFR と、関連 ADR が指す方式で書いている。旧方式（廃止した識別子・秘密・画面パス）を残していない
- 要件に無い振る舞いを足していない
- テスト設計（何をどう検証するか）と、その VitePress リンクをこの PR に入れていない
- 仕様は domain、実現は変更する層。要求の再掲だけで層を埋めていない
- 仮置きが本番仕様として読める書き方になっていない。要件が既に決めたことは「未決」に残していない

## 段階 0（割り当て）

- 申し送りが、domain の ID と閉じる層に 1 対 1 で割当たっている。落ちた項目が無い
- FR の動詞が、1 意図 1 操作の一覧になっている（発行と承認などを 1 操作にまとめていない）
- 既存設計が正本と食い違う範囲を列挙し、旧方式の上に足す計画になっていない

## 段階 1（データ系）

- 不変条件の保証に「UI で入力できない」だけを書いていない
- 直 INSERT / UPDATE でも破られない閉じ方（制約、RLS の列制限、検証付き definer）がある。usecase のロックだけになっていない
- RLS UPDATE は、誰かに加え、**変えてよい列**が書いてある。その操作に不要な列まで更新できていない
- 直接変更と関数経由のどちらが正か、食い違いがテーブルの「設計上の補足」にある
- `security definer` を出すなら、関数名、`GRANT EXECUTE` の相手（付けないロールも）、`search_path`（既存 ADR 006 に合わせる）がある
- 本人確認に使う属性の比較の正（テーブルかクレームか）が 1 つに決まっている
- 同時実行で破れる条件は、破りうるすべての操作で同じ閉じ方を指している。方式が「レビューで確定」のまま残っていない
- 要件が限定するアクターを、UI だけでなくポリシーと関数の両方で拒否している。片方だけの関門にしていない

## 段階 2（バックエンド）

- 段階 0 の操作一覧が、1 ファイル 1 操作になっている
- usecase は段階 1 の DB 側の閉じ方を呼ぶ。同じ不変条件をアプリだけで再実装していない
- 失敗の意味が、本人に理由を返す場合と、他人の存在を推測させない場合で分かれている（要件が両方求めるとき）
- 要件が「相手に分からない」としている事実を、成功/失敗やエラー文で漏らしていない

## 段階 3（フロントエンド）

- 画面の Primary は 1 つ
- 要件が「確かめられる」としている対象は、既に別状態のときも出る（未所属のハッピーパスだけにしていない）
- 空状態と失敗時に、説明と次の行動がある
- ルートは実装を見た結果か「未記載」。推測のパスを確定扱いしていない
