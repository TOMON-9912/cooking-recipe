# 設計書レビュー観点

`review-design` が読む。プロダクト固有の正解は `docs/01_requirements`〜`docs/04_decisions` を正とし、ここにコピーしない。

## 1. 標準

### 1.1 要件との対応

- 要件定義があり、ステータスが確定している
- 各 FR / NFR が、仕様（主に domain）か設計（変更する層）のどれかに落ちている
- 受け入れ条件を、操作と失敗の意味で再現できる
- 「設計への申し送り」が、決めたことまたは未決（決めるまで禁止することつき）になっている
- 要件に無い振る舞いを足していない。足したくなったら `/requirements` へ戻す案にする
- ADR と domain / database / application / ui が同じ方式を指している

### 1.2 仕様と設計を混ぜない

- domain: ルール・状態・権限・失敗の意味。テーブル名や手順を正にしていない
- application: 内部の流れとパス。要求の再掲だけになっていない
- database: カラム・制約・RLS。業務ルールの正は domain
- ui: 主目的 1 つ、ルート、空状態、失敗時。usecase の内部手順を書いていない
- テスト設計（何を検証するか）が、この設計 PR に入っていない

### 1.3 層と操作

- 変わる層だけ書いている。空の設計書を量産していない
- ひな形の章が、決めたことまたは「未記載 / 状態なし」で埋まっている
- 操作がドメインの動詞で 1 意図 1 行になっている（発行・一覧・取り消し・承認を 1 ファイルに固めすぎていない）
- 画面のルートと成功遷移は、実装の page / フォームを見た結果である。未確認なら「未記載」。推測のパスを確定扱いしていない

### 1.4 未決

- 仮置きが本番仕様として読める書き方になっていない
- 「レビューで確定」とある項目が、このレビューの問いになっている
- 既存フローを壊さない約束（例: 家族作成）が、影響表かポリシー変更に落ちている

## 2. セキュリティ（厚く見る）

このプロダクトは家族が共有の境界である。画面の非表示だけでは足りない。usecase と DB（RLS または `security definer` 関数）の両方で同じ拒否になるかを見る。

### 2.1 認証

- 未ログインで承認・発行できないことが、ルートと失敗の意味で書かれている
- 「ログイン後に自動で戻る」を要件が不要としているなら、設計が必須扱いにしていない
- ゲストと本登録の区別がある。FR が本登録限定なら、UI だけでなく DB 側の関門がある
- メール確認済みを本人確認の土台にするなら、確認の仕組みを新設せず、既存 signup に乗っている

### 2.2 認可

- 誰が・何を・どの条件で、読む / 作る / 変える / 消す、が domain にある
- オーナー限定（発行・一覧・取り消し）が、メンバーや未所属では拒否される
- 他人の招待を見る・承認することが拒否される（NFR-05）
- 家族 ID や案内 URL だけでは所属が増えない（NFR-01）
- 既存の緩いポリシー（例: `family_members` の `user_id = auth.uid()` だけ）を、どう閉じるかが書いてある
- 直接 INSERT / UPDATE と、関数経由の更新のどちらが正か、食い違いが「設計上の補足」にある

### 2.3 秘密・トークン・URL

- 秘密を持つなら: 本体を保存しない、ログに出さない、再表示しない、推測できない長さ、ハッシュ照合
- 秘密を持たないなら: 本人確認はログイン中の属性（メールなど）で行う。URL を持つことが認可にならない
- 方式が ADR と一致している。トークン案と宛先指定案が文書間で混在していない

### 2.4 PII と情報漏洩

- 宛先メールなど、本人以外が読める経路（SELECT、一覧、エラー、プレビュー）が閉じている
- オーナーに、宛先が登録済みかどうかが分からない（NFR-04）。発行の成功/失敗やエラー文で推測できない
- 承認前に見えるのは、要件が許した範囲だけ（例: 家族名。メンバーとレシピは出ない）
- 失敗理由の区別が、他人の招待の存在を推測させるオラクルになっていない。FR の「理由が分かる」と NFR の「推測させない」の両立が書いてある
- 照会関数の戻り値が、ID・メンバー・他家族を含まない

### 2.5 同時実行と上限

- 同じ招待の同時承認で、所属が 2 行にならない
- 1 人 1 家族が、作成時だけでなく参加時の競合でも拒否される。一意制約か関数内直列化か、選んだ理由がある
- 人数上限があるなら、同時承認での超過を、二重所属と同じ仕組みで扱えるかが書いてある
- 途中失敗で、所属だけ増える / 招待だけ使用済み、が残らない

### 2.6 DB 関数と RLS

- `security definer` を使うなら: 実行権限、検証を関数内で行うこと、RLS 回避を最小にすること、が設計にある
- ヘルパー（`get_my_family_ids` 等）の再帰問題を、既存 ADR 006 と矛盾させない
- ゲスト判定をポリシーと関数の片方だけに置いて、もう片方で抜けていない
- 取り消しは DELETE で消えて履歴も認可も消えるのか、状態列で残すのかが、承認拒否と一致している

### 2.7 入力と境界

- メールアドレスの正規化（大文字小文字など）が、一致判定の正として書いてある
- 重ね発行の防止が、取り消し済み・期限切れ・承認済みと区別されている
- 画面に出さない操作（強制追加、ゲストの発行）が、API / Action / RLS でも拒否される
